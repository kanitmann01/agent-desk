# T11: Operations and governance plugins (4)

Part of #97.

## Context

The desk should be able to report on itself: which plugins are unhealthy, which updates exist, what left the machine, and whether the desk is still inside policy. These four cards make the runtime legible without a log file.

## Scope

| id | Question | Source | Lead element |
|---|---|---|---|
| `plugin-health` | Which plugins are stale, pilot, or awaiting consent? | desk-state | status + list |
| `update-radar` | What updates exist, and do they widen scope? | desk-state | list + delta |
| `audit-digest` | What left the machine this week? | desk-state | metric + table |
| `compliance-posture` | Are we still inside policy? | desk-state | status + checklist |

- `desk-state` reads runtime, audit, and policy state only. No user file access.
- `plugin-health` groups by state (stale, pilot, consent pending, disabled) and names the first three offenders.
- `update-radar` shows available updates and marks the ones that widen scope.
- `audit-digest` counts egress events in the window by destination, never payloads.
- `compliance-posture` checks policy mode, signature requirement, revoked publishers, and stale plugins, and returns attention with the first failing check.
- Categories `operations`, tags for the job.

## Acceptance criteria

- [ ] All four validate as v2 and appear in the bundled catalog.
- [ ] Each executes against desk-state fixtures and returns the documented lead value with as-of.
- [ ] `plugin-health` with three unhealthy plugins lists three, and with none returns the ok state.
- [ ] `update-radar` marks a widening update and leaves a narrowing one unmarked.
- [ ] `audit-digest` counts egress by destination and never includes a payload or body.
- [ ] `compliance-posture` returns attention with the failing check when a publisher is revoked, and ok when all checks pass.
- [ ] No plugin reads a user path.

## Tests

Registry package seam: fixtures for runtime state, audit JSONL, and policy, plus state matrix tests.
