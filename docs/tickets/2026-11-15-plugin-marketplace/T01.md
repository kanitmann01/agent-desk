# T1: Manifest v2, ten render elements, and sample render

Part of #97.

## Context

Manifest v1 validates exact keys, and the executor runs only `metric` and `text`. Any other element kind is silently dropped, so a plugin author cannot tell a typo from a feature. The marketplace needs richer cards and a real sample render before a detail page can show one. This ticket widens the declarative surface only. No executable code is added.

## Scope

- Validator accepts `schemaVersion: 1` unchanged and `schemaVersion: 2` with new fields: `category` (finance, time, communication, research, operations, command, reference), `tags` (<= 8 slugs), `icon` (fixed enum), `summary` (<= 120 chars), `description` (plain text), `highlights` (exactly 3), `sample` (relative path to a JSON fixture), `requires` (plugin ids), `minHost` (semver range). Unknown keys stay rejected.
- Validator checks: sample file exists, parses as JSON, <= 32 KB; category and icon enums; tags and requires are safe ids; `requires` graph has no cycles and never self-references.
- Runtime normalizes v1 to v2 defaults (category `reference` only for known reference plugins, otherwise `operations`; empty tags; generic icon; summary from name) so installed v1 plugins keep rendering.
- Executor implements ten element kinds: metric, text, delta, progress, list, table, sparkline, status, timeline, checklist. Every element reads its payload from the envelope `{value, asOf, source, state}`.
- Enforce element caps: list <= 8 rows, table <= 20 rows, sparkline 12 to 30 points. Violations are validator errors.
- Unknown element kind is a hard error at validation and at execution (`plugin:unknown-element`), never dropped.
- Add a pure `render_sample(plugin_dir)` that executes the packaged sample fixture through the same executor and returns the payload, without reading any user file. This is what the detail page will call in T5.

## Acceptance criteria

- [ ] A v1 manifest fixture still validates and executes with no changes.
- [ ] A full v2 manifest validates; removing or breaking each new field yields a validator error that names the field.
- [ ] An unknown top-level key is rejected; an unknown element kind is rejected at validation and at execution with a message naming the kind.
- [ ] All ten element kinds render from a fixture sample; a missing binding renders the blank state, not `0`.
- [ ] `render_sample` works for a plugin with no workspace configured and reads no user path.
- [ ] The 84-test targeted baseline stays green.

## Tests

- extend `tests/test_plugins_execute.py` for all ten kinds plus unknown kind
- new `tests/test_plugins_sample.py` for `render_sample`, including a missing sample fixture
