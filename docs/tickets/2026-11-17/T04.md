# T4: One rail: Peers leaves, Activity and Capabilities move under Settings

Part of specs/007-real-data-audit-and-settings.md (demo 2026-11-18). Reproduced
2026-11-17: the rail carries ten destinations, three of which do not earn the slot.
/activity renders an empty page (only the Collapse control). /capabilities duplicates
Marketplace (install/update) and Settings (endpoint, gates): its six gate cards plus a
Company endpoint block live on their own page. /peers is not wanted on the demo rail.

## Context

Two rails exist: React Rail.tsx for the dashboard and pages.py _rail() for every
server-rendered page (they must change together), both with per-destination icons and an
active state. Settings has one long section stack; capabilities_view and activity_view are
independent renderers.

## Scope

- Peers leaves both rails. /peers still serves its page when typed, so bookmarks and the
  peers API keep working; nothing else changes.
- /activity answers 302 to /settings/activity. /capabilities answers 302 to
  /settings#capabilities. Both old views keep their renderers; the settings page composes
  them so no content is lost.
- Settings grows two anchors: #capabilities (the six gates and the Company endpoint block,
  reusing capabilities_view's renderer inside a Settings card) and a card linking to
  /settings/activity (the audit log screen, T5).
- /settings/activity is a full page with the Settings rail entry active, one card, a kind
  filter, and a CSV export button; it is not a scroll anchor on the already long page.
- Tests: both redirects answer 302 to the right target; the rail HTML on a server page and
  the React rail contain no Peers link; /settings HTML contains the gates block and the
  activity card.

## Acceptance

1. No rail shows Peers; /peers still 200s.
2. /activity 302s to /settings/activity; /capabilities 302s to /settings#capabilities.
3. Settings renders gate cards and an Activity entry point in its own cards.
