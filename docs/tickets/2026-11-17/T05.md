# T5: One audit trail behind Settings > Activity

Part of specs/007-real-data-audit-and-settings.md (demo 2026-11-18). Reproduced
2026-11-17: "every trace of what the user does" is spread across module-local records.
llm.* and marketplace.* rows are written by their own callers; the Activity page renders
none of them; Settings shows fragments; there is no single newest-first list with a kind
filter and an export.

## Context

app.py already owns audit_store.record(...) call sites and an export.csv route; the store
is SQLite with action/target/outcome/time columns. The gap is coverage, one reader, and
one screen. The existing /audit/tail JSON route stays for scripts.

## Scope

- Enumerate the mutating routes and the model calls (wizard build, marketplace install /
  update / remove, registry refresh, instance create/pick/stage/confirm/evaluate, memory
  sweep, settings save, endpoint test, gate re-test, layout save) and record one audit row
  each. Actions are dotted verbs (plugin.instance.confirm, llm.evaluate, settings.save),
  targets are ids or file names only, never paths or secrets.
- One reader: audit_store.tail(conn, limit, kind) newest first, kind prefix filter, plus
  the existing CSV export filtered the same way.
- Settings > Activity page renders the reader: time, action, target, outcome, newest first,
  a filter select (All, Plugins, Model, Settings, Registry), and Export CSV. Empty state
  names what will appear once the user acts.
- Tests: a confirm and a model call each produce a row visible through the reader and the
  page; the filter narrows; export contains the same rows; no row contains a file path.

## Acceptance

1. Confirm a tracker, then Settings > Activity lists the confirm and, when a call ran, the
   evaluation, newest first.
2. Filtering by Plugins hides model rows.
3. Export CSV contains the visible rows.
