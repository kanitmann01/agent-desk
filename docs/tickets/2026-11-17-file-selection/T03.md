# T3: Instance setup is plugin-generic

Part of specs/006-file-selection-and-wizard-fix.md (issue #123). The per-instance setup
flow (create, pick, stage, preview, suggest, confirm, accept-outside) and its dashboard
card contract are pinned to one bundled tracker id. Any other plugin that declares the
workbook config kind gets nothing: the runtime treats it as a tracker only if it is that
one id, so a wizard-built or third-party config-backed plugin cannot be configured.

## Context

The instance store, setup flow, and runtime card expansion all special-case one plugin id
(a module constant pins the tracker). The HTTP endpoints are already id-parameterized;
the pin lives in which plugin the flow will serve and which installed plugin the runtime
expands into per-instance card keys. This ticket removes the pin so every config-backed
plugin participates on the same terms, with the same granted/confirmed read gate, the
same instance cap, and the same card-key expansion (`<plugin id>~<instance id>`).

## Scope

- Any installed plugin whose manifest declares supported config kinds gets instances:
  create, pick, stage, preview, suggest, confirm, accept-outside all serve it through the
  existing endpoints, with the existing config error vocabulary and HTTP envelope.
- The runtime expands one instance-capable install into one dashboard card per confirmed
  instance, and shows the wireframe with a Set up entry when none is confirmed yet, for
  any such plugin, not just the historical one.
- The granted/confirmed read gate is enforced per plugin id and instance: a plugin reads
  only its own granted, confirmed file; nothing about one instance's grant leaks to
  another plugin.
- The instance cap (default 6, setting-overridable) applies uniformly.
- The aliased instance pattern (a plugin that resolves to a named instance of another)
  keeps working unchanged.
- No plugin code changes anywhere: the manifest declaration is the only opt-in.

## Acceptance criteria

- [ ] A fresh fixture plugin that declares the workbook config kind (and is not the
      historical tracker) supports the full chain over real HTTP: create instance, pick
      (with the injected fake picker), stage, preview, confirm, and then reads exactly
      the confirmed file.
- [ ] Its dashboard card appears per instance under the `<plugin>~<instance>` key, with
      the wireframe and Set up entry before any confirm.
- [ ] The read gate refuses an ungranted or unconfirmed read for the new plugin with the
      existing error codes.
- [ ] The seventh instance is refused at the default cap, for any config-backed plugin.
- [ ] The historical tracker's existing tests pass unchanged (no behaviour change for
      it), and the alias pattern still resolves.
