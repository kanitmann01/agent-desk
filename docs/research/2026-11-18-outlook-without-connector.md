# Outlook mail on a locked-down laptop, without a connector

Status: decision-ready research note. Date: 2026-11-18. Scope: agent-desk (Nexuus Bot), Windows desktop, Python >=3.10, no admin rights, no terminal for the end user.

Verified baseline: commit `02ea418` plus the uncommitted spec 008 work present on this tree at the time of writing (specs/008-plugin-truth-and-outlook-brief.md, src/agentdesk/mail/brief.py, tests/test_mail_brief.py, tools/export-outlook.ps1, demo/outlook-inbox/ with six `.eml` files, edits to mail/core.py, plugins/execute.py, plugins/sources.py, marketplace/policy.py, marketplace/bundled-catalog.json, registry/index.json, validator/lint.py, the outlook-digest plugin files, and two test files). Any line number below is a reading aid, not a contract.

## Executive recommendation

Adopt the exported-`.eml` drop folder as the product's only mail ingestion contract, and build the Outlook brief on top of it. The app never talks to Exchange: no Microsoft Graph, no IMAP, no EWS, no PST/OST parsing, no COM inside the product. Outlook, or the user's own Power Automate flow, writes RFC 822 `.eml` files into a folder the host already watches (src/agentdesk/mail); the host parses headers with the standard library, ranks one message with an explainable rule set, and renders three subject-based reply starters inside the declarative Outlook plugin. Feeders in order of adoption: (1) manual Save as / drag-and-drop / Outlook on the web Download, guaranteed to work with new Outlook and needing no admin; (2) a personal Power Automate flow, Office 365 Outlook `Export email (V2)` plus OneDrive `Create file`, where tenant policy allows personal flows; (3) a checked-in mock inbox for CI and the demo. Classic Outlook COM export stays a development and demo helper only, because the end user has no terminal and new Outlook has no COM at all. This option needs no Entra app registration, no tenant consent, no new runtime dependency, and keeps every mail byte local.

## Why the folder contract wins

- It is the only option that needs nothing from IT: no Entra object, no consent screen, no admin role, no mailbox protocol, no new Python package.
- It matches what the repo already built. The reader, the settings field, the watcher, the audit and the plugin pipeline all exist; the missing piece is a brief and a documented feeder, not an integration layer (mail/core.py, mail/watcher.py, settings.py L32/L62, plugins/execute.py).
- It survives the new Outlook transition. COM dies with new Outlook (one Outlook doc; techcommunity post), EWS is blocked from 2026-10-01, and IMAP needs tenant admin consent. Save as and OWA Download are supported in both clients today.
- It keeps bodies out of the app by construction. The saved file may contain a body, but `parse_eml` never puts one on a record; no card, prompt, audit row or outbox draft can quote it (mail/core.py L45-117; specs/004 L273-285).
- It degrades honestly. No folder means an attention state that names Settings; an empty folder means "no .eml files yet"; a broken file is counted and skipped, not fatal.

## Feeders: how mail gets into the folder

1. Manual, zero setup, works everywhere. New Outlook: open the message, More actions > Save as, choose the folder and file type. Classic: File > Save As. Outlook on the web: select the message, Download, which saves .eml or .msg ([support article](https://support.microsoft.com/en-us/outlook/mail/save-an-outlook-message-as-a-eml-file-a-pdf-file-or-as-a-draft); [new Outlook and OWA steps](https://www.robert365.com/article/saving-emails-as-eml-file-in-the-new-outlook-or-owa); drag-and-drop in new Outlook produces .eml per the [Microsoft Q&A answer of 2026-06-09](https://learn.microsoft.com/en-us/answers/questions/5915469/how-can-i-drag-and-drop-a-msg-from-the-new-outlook)). This is the guaranteed path for a locked-down user. Its weakness is obvious: it is per-message, so the digest is only as fresh as what the user saved.
2. Power Automate personal flow, automatic, tenant permitting. Trigger `When a new email arrives (V3)` (Operation ID OnNewEmailV3) or a recurrence; action `Export email (V2)` (ExportEmail_V2, "Export the content of the email in the EML file format", Message Id required, Original Mailbox Address optional) returns the full message as binary; action OneDrive for Business `Create file` (CreateFile) writes it to a synced folder; the host polls that folder. Both connectors are Standard class ([Office 365 Outlook](https://learn.microsoft.com/en-us/connectors/office365connector/), [OneDrive for Business](https://learn.microsoft.com/en-us/connectors/onedriveforbusiness/)), and Microsoft 365 seeded licenses cover standard connectors ([licensing deep dive](https://learn.microsoft.com/en-us/power-platform/admin/power-automate-licensing/deep-dive-on-specific-license)). The failure modes are policy, not product: admins can block connector actions ([connector action control](https://learn.microsoft.com/en-us/power-platform/admin/connector-action-control)) or the connector pair with DLP ([DLP strategy](https://learn.microsoft.com/en-us/power-platform/guidance/adoption/dlp-strategy)); OneDrive Files On-Demand placeholders may download slowly or not at all offline. This is the same pattern the repo already chose for calendar (docs/research.md L298-304; src/agentdesk/calendar/core.py reads a OneDrive calendar_sync.json, no Graph, no COM). A header-only variant is possible: `Get emails (V3)` (GetEmailsV3, folder and filter parameters, `Top` default 10, max 1000, filters apply to the first 250 emails in a folder) returns Graph message fields including `internetMessageId`, `importance`, `receivedDateTime`, `from`, `toRecipients`, `ccRecipients` ([Graph message resource](https://learn.microsoft.com/en-us/graph/api/resources/message)); a Compose plus Create file step could write an RFC 822 header-only `.eml` and never copy the body. That variant needs its date formatting tested against `format_header_ts`, so treat it as a DLP-driven follow-up, not v1.
3. Classic Outlook COM export script, dev and demo only. `tools/export-outlook.ps1` now exists as the header-only helper: it opens classic Outlook over COM, sorts the Inbox by `ReceivedTime`, restricts it to `-Days` (default 14, `-Limit` default 100), and writes one `.eml` per message with From/To/Subject/Date (RFC 1123)/Message-ID/In-Reply-To/Importance, then a blank line and deliberately no body. It exits 1 with a plain message when Outlook has no profile. It needs classic Outlook, a configured profile, and a terminal or scheduled task; the Object Model Guard can warn on cross-process object-model calls, and the outcome depends on antivirus health and Trust Center policy ([guard behavior](https://learn.microsoft.com/en-us/office/vba/outlook/how-to/security/security-behavior-of-the-outlook-object-model)). Because it writes headers only, a demo folder it produces carries no bodies; that is not true of a manual Save as of a whole message. The demo laptop in specs/008 L107-110 has Outlook.exe but no profile, which is exactly why the mock inbox is the rehearsed path. Never present this script as the end-user setup.
4. Mock inbox, for CI and the demo. Six checked-in header-only `.eml` files under demo/outlook-inbox/ (specs/008 G3) give a deterministic, privacy-free path for tests, screenshots and the browser walkthrough; the people and domains are invented, not real mail.

## Importance ranking and reply starters

The in-flight brief already answers "which one matters most" without a model. The score is additive and every contribution becomes a reason string rendered as `topEmailWhy` (mail/brief.py L89-126): subject urgent words (up to +5), a question or trailing `?` (+2), `Importance: high` or `X-Priority: 1` (+5, low -2), addressed to the watcher's self address (+2), recency (+3 for <=2 h, +2 for <=24 h, +1 for <=72 h), a no-reply sender (-4). Candidates are limited to the last 72 hours (`TOP_HOURS` L20), ties break on newer timestamp, and an empty window returns `None` rather than an invented winner (L149-164). This is defensible for a briefing product precisely because it is explainable and offline: no prompt, no egress, no nondeterminism, and a test can pin the winner.

Limits that must be said out loud: `Importance` is optional metadata and many senders omit it; absence means unknown, not normal. The score is a heuristic, not an assessment of business impact, and the 72-hour window is folder-scoped. The UI should show the reasons, not just the name.

Reply starters (mail/brief.py L167-193) are three openers built from the subject line, labelled Direct, Clarify and Brief, with the `Re:` prefix stripped and the topic quoted. They are deliberately not drafts: no body was read, so the copy says only what the subject supports, and the window note says starters come from the subject line. If a starter is wired to the existing draft form, it may prefill the textarea; it must not write an outbox file or send anything on its own. Sending remains the user's act in their own mail client, which is already the posture of `write_reply` (mail/core.py L291).

Adding the corporate LLM later is allowed by the architecture but not needed now: `llm.py` can degrade cleanly (`LlmUnavailable` L56), and a header-only prompt could produce a more natural opener. Keep it out of v1 because it adds egress, latency and a hallucination surface for a feature that already works, and because the plugin declares `llm.allow false`.

## Fixture plan and test cases

Format decision: RFC 822 `.eml` files, parsed with the standard library `email.parser` (policy `compat32`, chosen in mail/core.py L79-L117 because `policy.default` silently drops unparseable address lists that reply-all needs). This is the same format Outlook Save as, OWA Download and Power Automate `Export email (V2)` produce, it needs no new dependency, and it can carry `Importance` / `X-Priority`. `.msg` is rejected: `olefile` exposes only OLE streams, so MAPI parsing would be new code, and `extract-msg` is GPL. PST is rejected on license and dependency grounds (libpff LGPL-3.0, alpha; libratom needs a C toolchain). Do not add a mailbox-format dependency to prove a product claim.

## What the UI must keep honest

| Situation | What the card may say | What it must never say or show |
|---|---|---|
| Mail is off (`mail_enabled` false) or no folder is chosen | Attention state naming Settings and the folder field: "Turn on mail in Settings, choose the folder your .eml exports land in, then re-test." No numeric bindings (plugins/execute.py `_outlook_status` returns attention with empty values; specs/004 L182) | A zero, "inbox zero", a sample digest, or "Outlook connected" |
| Folder path points at a missing or unreadable folder | The watcher's own cause, as plain language, plus the folder path and a retry action | A number, a silent retry loop, or an invented "waiting for Outlook" |
| Folder exists but has no `.eml` files | "No .eml files yet" plus the folder path and the name of the export helper (dev) or feeder (user) | "0 messages", "nothing needs you", or a sample payload |
| Folder has files, all unparsable | The parse-failure count and the folder path, if surfaced; at minimum do not call the folder empty | "No mail arrived" when files exist and failed |
| Fresh files present | Counts for the last 24 h, `threadRows` with `count msg · age`, topEmailSubject plus topEmailLine and topEmailWhy, three labelled starters, and the window note "From message headers only..." | Unread counts (no read flag exists), attachments, bodies, categories, calendar, delivery or read receipts |
| Without Outlook installed at all | The same folder-based states. The product does not detect or require Outlook | "Outlook is not installed" as an error, an Outlook version probe, or a repair prompt |
| New Outlook versus classic | Nothing changes; both can produce .eml files | Any instruction that requires classic Outlook, COM, File > Save As inside a script the user cannot run, or an add-in |
| Stale or repeated polling | `checkedAt` and the 24 h window; "as of" language where the age matters | "Live", "real-time", "synced", or a freshness claim the poll interval cannot support (`POLL_INTERVAL_S = 1800`) |
| Plugin installed with the sample | Sample values clearly stamped as a sample (specs/004 L143) | Real data mixed with sample data, or a sample stamp on live data |
| Reply starters | "Starters from the subject line"; each starter labelled Direct / Clarify / Brief; a starter may prefill the draft box | "Draft ready", "reply written", "suggested reply based on the email", or any send action |

## Risks and what we must NOT claim

Risks:

- Manual export is labour and staleness. The digest is only as complete as what the user saved; an empty folder can coexist with a full inbox. Mitigate with explicit "folder" language and a feeder guide, not with invented counts.
- Power Automate availability varies by tenant and SKU. Admins can block the connector or its actions, DLP can block the connector pair, OneDrive sync can be disabled or slow, and Files On-Demand can make a file a placeholder. The app cannot verify any of this; it can only show whether a file appeared.
- Full `.eml` exports copy bodies and attachments to disk and to OneDrive. Endpoint DLP may audit or block file access on enrolled devices ([endpoint DLP overview](https://learn.microsoft.com/en-us/purview/endpoint-dlp-learn-about)); the app's own audit only records the folder basename (mail/watcher.py), but the folder is Outlook's data, not the app's. The checked-in COM helper avoids this by writing headers only; manual Save as and `Export email (V2)` do not. If Security objects, use the header-only flow variant or a local-only folder outside OneDrive.
- Header-only ranking is approximate. Importance may be absent, subjects can be uninformative, and an aggressive no-reply penalty can bury a legitimate automated approval request. Keep the reason line visible and the window note prominent.
- The in-flight brief's "empty folder" branch keys on `if not messages` (execute.py `_outlook_status`). A folder full of unparsable files would read as empty. Fix by distinguishing "no `.eml` files" from "files present but none parsed" before shipping the copy.
- The plugin docs were partly stale and are being fixed in flight: README and skills/mail-overview now describe the six rendered bindings and the header-only source, but docs/design/plugin-authoring-v2.md L87-103 still lists `unread` and the old vocabulary. Fix the authoring doc in the same change, or the reference the next author uses lies. The updated widget also still omits the emitted `windowNote`, so the card has no scope footer unless a text element renders it; add one, because that note is the product's own honesty line.
- New Outlook and classic diverge. New Outlook has no COM (one Outlook doc; techcommunity post) and drag-and-drop yields .eml; classic can still Save As and drag .msg. Any instruction that assumes classic will fail on the default-future client.
- The demo laptop has no Outlook profile (specs/008 L107-110). The mock inbox is the rehearsed path; the COM script proves only the file shape, not the user journey.
- The product has no installer (docs/known-limitations.md), so there is no autostart and no background service. The watcher polls only while the app runs; do not imply always-on ingestion.

Must not claim:

- "Reads your Outlook" or "connected to Outlook". It reads a folder of exported files.
- "Live", "real-time", "synced", "mirrored", "full inbox", "all mail", "sent items", "unread", "read receipts", "categories", "attachments", "calendar", "delivery status".
- "The most important email" as an objective fact. Say "the message that scored highest, and why" or "most worth opening in this folder".
- "AI reply" or "draft reply". The starters are templates from the subject line; say so.
- "No admin needed" for IMAP, Graph, EWS, add-ins or PST parsing. IMAP requires tenant admin consent per Microsoft's own doc; Graph delegated consent can be blocked by tenant policy; EWS is retired for third-party apps.
- "Zero setup" when the automatic path is a Power Automate flow or a OneDrive folder; "no connector" means no app registration and no admin consent, not "no Microsoft 365 dependency".
- "Outlook is not installed" as an error state. The product does not care.
- "Bodies are read and discarded" in user-facing copy. The honest line is "bodies are never put on a record, card, audit row or prompt"; the exported file itself may contain one, and that file is outside the app.
- "The digest covers your mail". It covers the folder, for the 24 h window, for the files that were exported.
- "Tests prove Outlook compatibility". Tests prove the .eml shape and the rules; the real-machine export is a separate manual check.
- "Reply suggestions are safe to send". They are openers; sending is the user's act.
- "Install works" until registry pins and the bundled catalog are rebuilt and the install test passes (specs/008 G1).
- "No new dependency" while adding `extract-msg`, `olefile`, `libratom`, `libpff` or pywin32. The mail path must stay standard library.
- "Power Automate is sanctioned by IT" without a tenant check. The app only sees whether a file arrived.
- "No cloud copy" when the flow uses Export email (V2) into OneDrive. There is a cloud copy; say where it is.

## Open questions for the decision owner

1. Does Security accept full `.eml` copies on disk and OneDrive, or must the recommended feeder be the header-only flow variant? This changes the flow recipe, not the app parser.
2. Who owns and tests the Power Automate template on a real tenant, and which SKU is the demo tenant? The template must be imported by the user in a browser, which the persona can do, but someone has to verify the tenant allows personal flows.
3. Does the demo need the COM helper at all, or is the checked-in mock inbox enough for the walkthrough? specs/008 G3 asks for both; the app does not need either at runtime.
4. Should parse failures surface on the card (`unparsed` count in `view()`), or stay in the audit log? The current honesty rule says attention states must not carry numbers, but "files exist and none parsed" is a distinct state from "empty".
5. Is a starter allowed to prefill the existing draft textarea, or is it display-only in v1? Prefill is safe if it never writes the outbox until the user accepts.
6. Upgrade `outlook-digest` in place to 0.3.0 with `outlook-brief`, or add a second plugin? In-place keeps one mail card and one skill; the manifest id and skill stay stable, but every pin and screenshot must be refreshed.
7. Who signs off the README and binding-vocabulary truth fixes? They are part of the same "no invented data" promise as the card.
